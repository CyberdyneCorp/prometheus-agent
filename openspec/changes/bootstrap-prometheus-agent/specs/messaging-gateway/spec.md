# Messaging Gateway

## Purpose
The messaging gateway is the single long-running daemon per Prometheus home that owns sessions, agents, schedulers and messaging adapters, and that every local surface (CLI-in-TTY, TUI, desktop, dashboard, ACP) attaches to over a loopback, ticket-authenticated WebSocket speaking a versioned JSON-RPC 2.0 protocol generated from typed definitions. It routes every inbound event to a deterministic session lane under an explicit ProfileScope, applies authorization, pairing, busy and rate-limit policy taken only from typed configuration, and delivers replies through a durable outbox so that no reply is lost or duplicated across restarts.

## ADDED Requirements

### Requirement: One gateway daemon per home
The system SHALL run at most one gateway daemon per Prometheus home, guarded by an exclusive lock on `<home>/run/gateway.lock`, and SHALL publish its discovery file `<home>/run/gateway.json` exactly as defined by `workspace-architecture`. `prometheus daemon run` SHALL run the daemon in the foreground, `prometheus daemon start` SHALL start it detached and exit 0 if it is already running, `prometheus daemon ensure --json` SHALL start it when absent and print one JSON object `{rpc_url, control, instance_id, build_id, rpc_protocol}` for clients that spawn it (desktop, ACP), `prometheus daemon stop` SHALL request a graceful drain and `prometheus daemon status` SHALL print process state (pid, uptime, build), while `prometheus gateway` subcommands (`status`, `reload`, `outbox`) SHALL manage messaging adapters and delivery, `prometheus gateway status` printing per-profile and per-adapter state. The daemon SHALL exit 0 after a requested graceful stop, 78 on a configuration error or credential lock conflict that leaves nothing able to run, 75 when the home lock is already held by another daemon (as in `workspace-architecture`) or when it exits to be restarted by its supervisor (`prometheus daemon restart`, signed self-update), and 1 on any other fatal error; supervisor units generated by `prometheus daemon install-service` SHALL restart on 75 and 1 and SHALL NOT restart on 78.
**Milestone:** M2

#### Scenario: Second foreground daemon refused
- **GIVEN** a gateway daemon is running for home `~/.prometheus` with pid 4242
- **WHEN** the user runs `prometheus daemon run` against the same home
- **THEN** the system SHALL exit with code 75 and print "gateway already running for ~/.prometheus (pid 4242)"

#### Scenario: Idempotent start
- **GIVEN** a gateway daemon is already running
- **WHEN** the user runs `prometheus daemon start`
- **THEN** the system SHALL exit 0 without spawning a second daemon

#### Scenario: Stale endpoint file after crash
- **GIVEN** `<home>/run/gateway.json` names a pid that no longer holds `gateway.lock`
- **WHEN** a new daemon starts
- **THEN** the system SHALL acquire the lock, overwrite `gateway.json` and start normally

#### Scenario: Invalid config does not crash-loop
- **GIVEN** the default profile's `config.toml` sets `busy.input_mode = "loud"`
- **WHEN** the supervised daemon starts
- **THEN** the system SHALL report the validation error naming `busy.input_mode`, exit 78, and the supervisor SHALL NOT restart it

### Requirement: Loopback client attachment
The gateway SHALL accept client connections only on a loopback WebSocket listener (`daemon.rpc.bind` in `<home>/daemon.toml`, default `127.0.0.1:0` meaning an ephemeral port recorded as `rpc_url` in `gateway.json`), SHALL reject a non-loopback `daemon.rpc.bind` value at config validation, and SHALL authenticate each connection only with a single-use ticket obtained over the control channel as defined by `workspace-architecture` (30 s expiry, bound to `instance_id`, one profile and one purpose, carried as a WebSocket subprotocol) followed by `rpc.hello`; a connection that fails authentication SHALL be closed with WebSocket close code 4401 and a browser upgrade whose `Origin` is not the dashboard's own origin SHALL be closed with 4403.
**Milestone:** M2

#### Scenario: Wrong token rejected
- **WHEN** a client upgrades with a ticket the control channel never issued
- **THEN** the system SHALL close the connection with code 4401 and SHALL NOT process any further frames from it

#### Scenario: Ticket is single use
- **GIVEN** a ticket issued over the control channel was already used by one connection
- **WHEN** a second connection presents the same ticket
- **THEN** the system SHALL close the second connection with code 4401

#### Scenario: Public bind refused
- **WHEN** `daemon.rpc.bind = "0.0.0.0:7777"` is configured
- **THEN** the system SHALL fail validation with an error stating that the client listener is loopback-only and remote access goes through the relay

### Requirement: Versioned typed RPC protocol
The gateway SHALL serve exactly the client protocol owned by `workspace-architecture` (handshake `rpc.hello`, protocol version `<major>.<minor>`, schema `schema/rpc.json`, its JSON-RPC error table and WebSocket close codes) and SHALL NOT define its own handshake, version identifier or error codes; in particular it SHALL answer an undeclared method with error `-32601`, params that fail schema validation with error `-32602` naming the offending field, and an `rpc.hello` whose major version differs from its own with error `-32008` followed by close code 4426, while accepting any lower or higher minor version of the same major.
**Milestone:** M2

#### Scenario: Undeclared method
- **WHEN** an authenticated client calls `session.frobnicate`
- **THEN** the system SHALL return JSON-RPC error `-32601` and SHALL NOT invoke any handler

#### Scenario: Missing parameter
- **WHEN** a client calls `session.send` without the required `session_id`
- **THEN** the system SHALL return error `-32602` whose data names `session_id`

#### Scenario: Older minor client is accepted
- **GIVEN** the gateway speaks protocol `1.4`
- **WHEN** a client sends `rpc.hello` with protocol `1.2`
- **THEN** the system SHALL accept it and SHALL NOT emit event types introduced after minor 2 to that client

### Requirement: Event subscription and owned replay
The gateway SHALL stamp every session event with a per-session monotonically increasing `seq` and the daemon `epoch`, SHALL retain events with the limits defined by `workspace-architecture`, and SHALL serve `session.events.since {session_id, last_seen}` only for sessions whose profile is within the connection's ProfileScope, answering a session outside that scope with error `-32002` without disclosing whether it exists; a `last_seen` older than the retained window SHALL return `truncated: true` so the client reloads the transcript from storage.
**Milestone:** M2

#### Scenario: Reconnect resumes without gaps
- **GIVEN** a client last saw `seq` 120 of a session and 15 newer events are retained
- **WHEN** it reconnects and calls `session.events.since` with `last_seen = 120`
- **THEN** the system SHALL deliver events 121 through 135 in order before any live event

#### Scenario: Foreign profile session is invisible
- **GIVEN** a connection scoped to profile `work`
- **WHEN** it subscribes to a session owned by profile `personal`
- **THEN** the system SHALL return error `-32002` and deliver no events

### Requirement: Profiles served by one daemon
The daemon SHALL serve every profile under its home, starting for each profile exactly the adapters that profile's own `config.toml` enables, and SHALL bind each activity (inbound routing, turns, tool calls, agent eviction, shutdown flush, deferred callbacks, notifications, outbox delivery) to the owning profile's ProfileScope resolved from the session record, never from process environment or the launch profile. Daemon-wide keys (`daemon.rpc.*`, `gateway.http.*`, `gateway.relay.*`, `gateway.on_all_adapters_down`) SHALL be read only from `<home>/daemon.toml` and SHALL fail validation when set in any profile's `config.toml`, including `default`'s. All per-profile gateway state (routes, pairing, identities, outbox, policies, media cache, hooks) SHALL be stored in the owning profile's `state.db` or under that profile's home, daemon-wide runtime files (`gateway.lock`, `gateway.json`, `clean_shutdown`) SHALL live under `<home>/run/`, and no gateway path SHALL be computed from a hardcoded home or the process environment after startup.
**Milestone:** M2

#### Scenario: Eviction flushes into the owning profile
- **GIVEN** an idle agent for a `work` session is evicted by a sweep started outside any turn
- **WHEN** its memory flush runs
- **THEN** the system SHALL write into `work`'s memory store and SHALL NOT touch the default profile's store

#### Scenario: Daemon-wide key in a secondary profile
- **WHEN** profile `work`'s `config.toml` sets `daemon.rpc.bind`
- **THEN** the system SHALL fail validation with an error stating the key is only valid in `<home>/daemon.toml`

#### Scenario: Profile added while running
- **GIVEN** the daemon is running
- **WHEN** the user creates profile `side` with Telegram enabled and runs `prometheus gateway reload`
- **THEN** the system SHALL start `side`'s Telegram adapter without restarting other profiles' adapters or sessions

#### Scenario: Pairing written to the owning profile
- **GIVEN** profile `work` with Telegram enabled under the shared daemon
- **WHEN** a pairing code is issued to a `work` Telegram user
- **THEN** the pending entry SHALL be stored in `work`'s `state.db` and `prometheus -p work pairing list` SHALL show it while `prometheus pairing list` SHALL NOT

### Requirement: Routing identity and deterministic session keys
Every inbound event SHALL be resolved to one immutable routing identity (receiving adapter instance, owning profile, platform, scope id, chat id, chat type, thread id, canonical sender id, and linked person id when present) before any session key is derived, and an event whose owning profile is not served SHALL be dropped with one WARNING per adapter per hour, never routed to the default profile. The system SHALL derive every conversation key as `<profile>:<platform>[@<scope_id>]:<chat_type>:<chat_id>[:t:<thread_id>][:u:<participant_id>]` with `chat_type` in `dm`, `group`, `channel`, `thread`, or as `<profile>:person:<person_id>` for shared cross-platform DMs, where `<profile>` is always the literal profile name (including `default`) and all ids are the adapter's canonical ids percent-encoding `:` and `%`.
**Milestone:** M2

#### Scenario: Default profile key
- **GIVEN** a Telegram DM from chat `123` in the default profile
- **WHEN** the key is derived
- **THEN** the system SHALL produce `default:telegram:dm:123`

#### Scenario: Profile names never alias
- **GIVEN** profiles `default` and `main`
- **WHEN** the same Telegram chat `123` reaches each
- **THEN** the system SHALL produce `default:telegram:dm:123` and `main:telegram:dm:123`

#### Scenario: Separator in an id is escaped
- **WHEN** a Matrix room id `!abc:example.org` is keyed
- **THEN** the key SHALL contain `!abc%3Aexample.org` so it parses back to the same fields

#### Scenario: Unserved profile route is dropped
- **GIVEN** a relay event addressed to profile `ghost` that does not exist
- **WHEN** the gateway admits it
- **THEN** the system SHALL drop it, log one WARNING, return admission result `dropped`, and create no session

### Requirement: DM, group and thread isolation
The system SHALL isolate DMs per canonical chat id (falling back to the canonical sender id when the platform has no chat id), SHALL append the participant id for non-thread group and channel conversations when `gateway.sessions.group_per_user` is true (default `true`), and SHALL share a thread conversation across participants unless `gateway.sessions.thread_per_user` is true (default `false`); both keys SHALL be overridable per platform under `gateway.platforms.<name>.sessions`.
**Milestone:** M2

#### Scenario: Group members isolated by default
- **WHEN** users A and B post in the same non-thread Discord channel
- **THEN** the system SHALL route them to two keys ending `:u:A` and `:u:B`

#### Scenario: Thread shared by default
- **WHEN** users A and B reply in the same Slack thread
- **THEN** the system SHALL route both to one key without a `:u:` suffix

### Requirement: Single-flight session routing
Resolving or creating the session for a routing key SHALL be single-flight: concurrent resolutions of one key, including concurrent `/new`, SHALL share one result so that exactly one session row and one routing transition are created, and internal events (background completions, cron deliveries, receipts) SHALL NOT advance the conversation's last-user-activity time.
**Milestone:** M2

#### Scenario: Burst of first messages
- **WHEN** five messages for a new key arrive within 10 ms
- **THEN** the system SHALL create exactly one session and route all five to it

### Requirement: Conversations never rotate on time
The system SHALL replace the session routed to a key only on an explicit `/new` or `/reset`, on stuck-loop suspension, or when the routed session is found ended in `state.db` (self-heal); elapsed idle or wall-clock time SHALL NOT start a new session, and the new session SHALL record `parent_session_id` of the replaced one and a `reset_reason` in `new`, `reset`, `suspended`, `stale_route`, `policy`. The gateway SHALL prune routing entries (key to session mapping, not transcripts) whose last activity is older than `gateway.sessions.route_max_age_secs` (default 7776000; `0` disables pruning; negative values fail validation) at most once per hour, and SHALL never delete session transcripts as part of route pruning.
**Milestone:** M2

#### Scenario: Month-old conversation resumes
- **GIVEN** a DM key last active 30 days ago
- **WHEN** the user sends a message
- **THEN** the system SHALL continue the same `session_id`

#### Scenario: Suspended session replaced
- **GIVEN** the routed session is suspended
- **WHEN** the next message arrives
- **THEN** the system SHALL create a new session with `reset_reason = "suspended"` and notify the user once that a fresh session started

#### Scenario: Pruned route keeps its transcript
- **GIVEN** a route last active 120 days ago
- **WHEN** pruning runs
- **THEN** the system SHALL remove the route, keep the session searchable in `state.db`, and a new message on that key SHALL start a new session with `reset_reason = "stale_route"`

### Requirement: Busy input policy from configuration only
While a turn is running for a key, the gateway SHALL handle non-command input according to the shared key `busy.input_mode` in `queue` (default; append as a follow-up turn), `interrupt` (stop the turn and start a new one with the merged input) or `steer` (inject into the running turn at its next model call), debouncing text with `gateway.busy.debounce_ms` (default 350) up to `gateway.busy.debounce_cap_ms` (default 1000), merging media follow-ups into the pending input without interrupting, and sending at most one busy acknowledgement per key per 30 seconds when `gateway.busy.ack` is true (default `true`); `input_mode` and each `gateway.busy.*` key SHALL be overridable per platform under `gateway.platforms.<name>.busy` (for example `gateway.platforms.telegram.busy.input_mode`), unknown values SHALL fail validation, and no environment variable SHALL affect busy behaviour.
**Milestone:** M2

#### Scenario: Unknown mode is a validation error
- **WHEN** `busy.input_mode = "loud"`
- **THEN** the system SHALL refuse to load the config with an error listing `queue`, `steer`, `interrupt`

#### Scenario: Steer reaches the running turn
- **GIVEN** `busy.input_mode = "steer"` and a turn executing tool calls
- **WHEN** the user sends "use the staging database instead"
- **THEN** the system SHALL deliver the text to the running turn before its next model call and SHALL NOT start a second turn

#### Scenario: Acknowledgement throttled
- **GIVEN** `gateway.busy.ack = true`
- **WHEN** three follow-ups arrive within 10 seconds during one turn
- **THEN** the system SHALL send exactly one busy acknowledgement

### Requirement: Command busy policy declared in the registry
Every slash command available in the gateway SHALL declare a `busy_policy` in `immediate` (run immediately, even mid-turn), `interrupt_then_dispatch` (stop the turn, then run), `queue` (run after the turn) or `reject` in the shared command registry owned by `cli`, validated when the registry is built so an undeclared or unknown policy fails the build; the gateway SHALL apply the declared policy in one dispatch layer before any input queueing, and a `reject` command sent mid-turn SHALL receive "Agent is running - /<command> can't run mid-turn. Wait for the response or /stop first." without interrupting the turn.
**Milestone:** M2

#### Scenario: Approval bypasses the queue
- **GIVEN** a turn is blocked waiting for an approval
- **WHEN** the user sends `/approve`
- **THEN** the system SHALL dispatch it immediately and SHALL NOT queue it behind the turn

#### Scenario: Config change rejected mid-turn
- **WHEN** the user sends `/model gpt-x` while a turn runs and `/model` declares `reject`
- **THEN** the system SHALL reply with the rejection text and the turn SHALL continue

#### Scenario: Unknown slash text is plain input
- **WHEN** the user sends `/notacommand hello` mid-turn
- **THEN** the system SHALL treat it as ordinary text under `busy.input_mode`

### Requirement: Queued turns run in FIFO order
Each `/queue <text>` SHALL produce exactly one separate turn, run in FIFO order without merging, up to `gateway.busy.max_queued` entries per key (default 16, beyond which the gateway replies "Queue full (16). Wait or /stop."); `/new` and `/reset` SHALL discard queued human input, while queued internal events (background completions, cron deliveries) SHALL survive `/stop`, `/new` and `/reset`.
**Milestone:** M2

#### Scenario: Two queued prompts
- **WHEN** the user sends `/queue A` then `/queue B` during a turn
- **THEN** the system SHALL run A as its own turn and then B as its own turn

### Requirement: Stop preserves the session
`/stop` SHALL cancel the running turn for the caller's key, cancel its background subagents, clear pending human follow-ups, persist the partial transcript with an interruption marker, and reply "Stopped. You can continue this session."; it SHALL NOT suspend or replace the session, and with no running turn it SHALL reply "No active task to stop."
**Milestone:** M2

#### Scenario: Continue after stop
- **GIVEN** the user stopped a turn
- **WHEN** the user sends a new message
- **THEN** the system SHALL continue in the same `session_id` with the interrupted turn visible in context

### Requirement: Gateway slash commands, quick commands and hooks
The gateway SHALL resolve slash commands only against the shared typed command registry entries whose surfaces include `gateway`, SHALL emit the `pre_command` hook (payload carrying the command name) before dispatch whose typed result is `continue`, `deny {message}`, `handled` or `rewrite {text}`, and SHALL run user `quick_commands` of kind `exec` inside the execution sandbox with a scrubbed environment, redacted output and the whole process tree killed after `gateway.quick_commands.timeout_secs` (default 30); a quick command whose name collides with a registry command SHALL fail validation.
**Milestone:** M2

#### Scenario: Hook denies a command
- **GIVEN** a hook returns `deny` with message "not here" for `/model`
- **WHEN** a user sends `/model`
- **THEN** the system SHALL reply "not here" and SHALL NOT run the built-in handler

#### Scenario: Quick command timeout
- **GIVEN** an exec quick command that sleeps 120 seconds and forks a child
- **WHEN** it runs
- **THEN** the system SHALL kill the process and its child after 30 seconds and reply that the command timed out

### Requirement: Slash command access tiers
When a platform scope configures `gateway.platforms.<name>.admins` (DMs) or `gateway.platforms.<name>.group_admins` (groups), only listed canonical user ids SHALL run every gateway command, and other authorized users SHALL run only `/help`, `/whoami`, `/stop`, `/new`, `/queue`, `/link` and the names in `gateway.platforms.<name>.user_commands`; with no admin list for a scope every authorized user SHALL have every command in that scope.
**Milestone:** M2

#### Scenario: Non-admin refused
- **GIVEN** `admins = ["111"]`
- **WHEN** user `222` sends `/model`
- **THEN** the system SHALL refuse with "This command is restricted to admins." while `/help` still works for `222`

### Requirement: Authorization order and fail-closed default
The gateway SHALL authorize an inbound sender in this order and stop at the first verdict: local clients attached over the loopback protocol (always allowed for their ProfileScope); adapters whose descriptor declares `authorization_is_upstream` (the relay) or a signed webhook; per-chat grants `gateway.platforms.<name>.allow_chats`; `gateway.platforms.<name>.allow_all = true`; approved pairings and linked identities; `gateway.platforms.<name>.allow_users`; an adapter-enforced policy only when its effective mode is `allowlist`; otherwise deny. Wildcards in `allow_users` SHALL fail validation, `allow_all = true` SHALL log a WARN on every start, no environment variable SHALL grant access, and a bot-authored message admitted by any rule SHALL still be refused while that chat's bot-loop guard is cooling down (default 60 seconds after 5 bot-to-bot exchanges within 60 seconds).
**Milestone:** M2

#### Scenario: Default deny
- **GIVEN** Discord enabled with no allowlist, pairing or grants
- **WHEN** an unknown user mentions the bot in a server channel
- **THEN** the system SHALL deny the message and start no turn

#### Scenario: Wildcard rejected
- **WHEN** `gateway.platforms.telegram.allow_users = ["*"]`
- **THEN** the system SHALL fail validation with an error pointing to `allow_all`

#### Scenario: Bot loop cooled down
- **GIVEN** two bots exchanged 5 messages in a channel within 60 seconds
- **WHEN** the other bot sends a sixth
- **THEN** the system SHALL refuse it until 60 seconds have passed

### Requirement: Documented pairing flow
For an unauthorized DM the gateway SHALL apply `gateway.platforms.<name>.unauthorized_dm` in `pair` (default), `ignore` or `decline` (Email defaults to `ignore`, and any configured `allow_users` makes the default `ignore`); in `pair` mode it SHALL reply with an 8-character code from `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` valid for 3600 seconds, stored only as a salted SHA-256 hash in `state.db`, limited to one request per sender per 600 seconds and 3 pending codes per platform per profile, and locking pairing for that platform for 3600 seconds after 5 failed approvals. A code SHALL be approvable only through `prometheus pairing approve <platform> <code>`, the RPC `pairing.approve` from an attached client of that profile, or the admin-only gateway command `/pair approve <code>`, all three listed by `prometheus pairing --help` and the generated docs; `prometheus pairing list|deny|revoke` SHALL manage pending and approved entries.
**Milestone:** M2

#### Scenario: Approval tolerates formatting
- **WHEN** the owner runs `prometheus pairing approve telegram "abcd efgh"`
- **THEN** the system SHALL normalize it to `ABCDEFGH`, approve the matching sender and notify them in the DM

#### Scenario: Lockout after failures
- **GIVEN** 5 failed approvals for `telegram` within the window
- **WHEN** a sixth approval is attempted with a valid code
- **THEN** the system SHALL refuse it with "pairing locked for telegram until <time>"

#### Scenario: Code never logged
- **WHEN** a pairing code is issued
- **THEN** no log line, trajectory or telemetry event SHALL contain the plaintext code

### Requirement: Per-user rate limiting (upgrade)
The gateway SHALL apply per-sender token buckets keyed by profile and canonical sender (or linked person) with `gateway.rate_limit.messages_per_minute` (default 20, burst `gateway.rate_limit.burst` default 10) and `gateway.rate_limit.turns_per_hour` (default 120), plus an optional `gateway.rate_limit.daily_cost_usd` (default unset) measured from the cost ledger; an over-limit event SHALL be dropped (not queued) with admission result `rate_limited`, the sender SHALL receive at most one "Slow down: rate limit reached, try again in <n>s." reply per window, admins and local clients SHALL be exempt, and every limit SHALL be overridable under `gateway.platforms.<name>.rate_limit`.
**Milestone:** M2

#### Scenario: Burst exceeded
- **GIVEN** default limits
- **WHEN** a non-admin sends 40 messages in 10 seconds
- **THEN** the system SHALL admit at most the burst plus refill, drop the rest with `rate_limited`, and send one slow-down reply

#### Scenario: Daily cost cap
- **GIVEN** `daily_cost_usd = 2.0` and a user whose turns today cost 2.05 USD
- **WHEN** the user sends a message
- **THEN** the system SHALL not start a turn and SHALL reply that the daily budget resets at local midnight

### Requirement: Per-chat policies (upgrade)
The gateway SHALL apply `[[gateway.chat_policies]]` entries matched by `platform` plus `chat_id`, `chat_type` or `user_id` (most specific match wins; ties fail validation), each able to set `model`, `toolsets`, `skills`, `system_prompt_append`, `busy`, `rate_limit` and `max_cost_usd_per_turn`; `toolsets` and `skills` SHALL only narrow the profile's enabled set (a name outside it or unknown fails validation), a policy SHALL be resolved once when a session is created and frozen for that session, and changes SHALL apply to new sessions only unless an admin runs `/policy apply --now`, which starts a new session with `reset_reason = "policy"`.
**Milestone:** M2

#### Scenario: Group gets a restricted toolset
- **GIVEN** a policy for Discord channel `555` with `toolsets = ["web"]`
- **WHEN** a session starts in that channel
- **THEN** the agent SHALL receive only the `web` toolset's tools

#### Scenario: Policy cannot widen
- **GIVEN** the profile enables only `web` and `file`
- **WHEN** a policy sets `toolsets = ["terminal"]`
- **THEN** the system SHALL fail validation naming `terminal` as outside the profile's toolsets

#### Scenario: Mid-session edit is deferred
- **GIVEN** an active session in a matched chat
- **WHEN** the policy's `model` is changed and the config reloaded
- **THEN** the current session SHALL keep its model and system prompt, and the next new session SHALL use the new model

### Requirement: Cross-platform identity linking (upgrade)
The gateway SHALL let an authorized user link sender identities on different platforms of the same profile into one person: `/link` SHALL reply with a 6-digit code valid for 600 seconds, and sending `/link <code>` from another already-authorized account SHALL link both to one `person_id` stored in `state.db`; `/unlink <platform>` and `prometheus identity list|unlink` SHALL remove links. When `gateway.identity.dm_mode = "shared"` (default `per_platform`) DMs from all linked accounts SHALL route to key `<profile>:person:<person_id>` and replies SHALL go to the platform of the most recent inbound message, while group conversations SHALL never merge; linking SHALL NOT grant authorization to an unauthorized account, and rate limits and per-user memory SHALL be keyed by `person_id`.
**Milestone:** M3

#### Scenario: Continue on another platform
- **GIVEN** Telegram user T and Signal user S are linked and `dm_mode = "shared"`
- **WHEN** S sends "and the second one?" after a Telegram DM conversation
- **THEN** the system SHALL continue the same session and reply on Signal

#### Scenario: Linking cannot bypass authorization
- **GIVEN** Signal user S is not authorized
- **WHEN** S sends `/link 482913`
- **THEN** the system SHALL apply the unauthorized-DM policy and SHALL NOT create a link

#### Scenario: Expired code
- **WHEN** a link code is used after 600 seconds
- **THEN** the system SHALL reply "Link code expired" and create no link

### Requirement: Durable delivery outbox (upgrade)
Every outbound message (turn replies, chunks, notifications, cron deliveries, approval cards) SHALL be written to the profile's `outbox` table in `state.db` with an idempotency key `<session_id>:<turn_id>:<part>` before the first send attempt and SHALL move through `queued`, `sending`, `sent`, then optionally `delivered` and `read`, or to `failed` or `unknown`; transient failures SHALL be retried with exponential backoff from 2 seconds up to 10 minutes for at most `gateway.outbox.max_attempts` (default 8) or `gateway.outbox.max_age_secs` (default 86400) then become `failed`; a send whose outcome is ambiguous (timeout after transmission) SHALL become `unknown` and SHALL NOT be resent unless the adapter can confirm non-delivery; `prometheus gateway outbox list|retry|drop` SHALL manage entries; parts of one reply SHALL be delivered in order.
**Milestone:** M2

#### Scenario: Reply survives a crash
- **GIVEN** a reply was written to the outbox and the daemon is killed before sending
- **WHEN** the daemon restarts
- **THEN** the system SHALL send that reply exactly once

#### Scenario: Ambiguous timeout not duplicated
- **WHEN** a Telegram send times out after the request was written
- **THEN** the entry SHALL become `unknown` and the system SHALL NOT resend it automatically

#### Scenario: Platform outage
- **GIVEN** Discord returns HTTP 503 for 20 minutes
- **WHEN** replies are produced during the outage
- **THEN** the system SHALL deliver them in order after recovery without user action

### Requirement: Delivery receipts surfaced (upgrade)
When an adapter declares `delivery_receipts` or `read_receipts`, the gateway SHALL update the outbox entry to `delivered` or `read`, emit a `message.delivery {session_id, outbox_id, state}` event to attached clients, and expose the state in `prometheus gateway outbox list`; entries in `failed` SHALL additionally notify the session's attached clients and, if configured, the profile's `gateway.home_channel`.
**Milestone:** M3

#### Scenario: Read receipt reaches the TUI
- **GIVEN** a TUI attached to a WhatsApp session
- **WHEN** the recipient reads the reply
- **THEN** the TUI SHALL receive `message.delivery` with `state = "read"`

### Requirement: Approval requests routed to every surface
The gateway SHALL deliver each tool approval request of a gateway session to the originating chat (as an interactive card where supported) and to every attached client of the same profile, accept the first valid resolution from the requesting user, a configured admin or a local client, update or retract the card on every other surface with the outcome and resolver, and treat expiry after `approvals.timeout_secs` (default 300), client detachment or card dismissal as denial.
**Milestone:** M2

#### Scenario: Resolved in the desktop app
- **GIVEN** an approval card pending in Slack and the desktop app attached
- **WHEN** the user approves in the desktop app
- **THEN** the system SHALL resume the tool call and edit the Slack card to "Approved once by <user> via desktop"

#### Scenario: Timeout denies
- **WHEN** no resolution arrives within 300 seconds
- **THEN** the system SHALL deny the tool call and mark the card expired

#### Scenario: Bystander cannot approve
- **WHEN** another non-admin member of the group taps Approve
- **THEN** the system SHALL ignore the tap and reply privately or ephemerally that only the requester or an admin may decide

### Requirement: Streaming to platforms
Token streaming to messaging platforms SHALL be governed by `gateway.streaming.enabled` (default `false`) and `gateway.streaming.transport` in `auto` (default), `draft`, `edit`, `off`, with `edit_interval_ms` default 800, `buffer_threshold` default 24 characters and `cursor` default `" ▉"`; `gateway.platforms.<name>.streaming.enabled = false` SHALL disable streaming for a platform while a per-platform `true` SHALL NOT enable it when the global switch is off; the final message SHALL replace the streamed draft in place via edit when the adapter supports editing, and otherwise be sent once with the draft deleted or left unsent.
**Milestone:** M2

#### Scenario: Per-platform cannot enable
- **GIVEN** `gateway.streaming.enabled = false` and `gateway.platforms.telegram.streaming.enabled = true`
- **WHEN** a Telegram turn runs
- **THEN** the system SHALL NOT stream and SHALL send only the final message

#### Scenario: Final edits the draft
- **GIVEN** streaming via `edit` on Discord
- **WHEN** the turn completes
- **THEN** the system SHALL edit the streamed message to the final text and SHALL NOT send a duplicate

### Requirement: Background and internal notifications
Notifications for background processes and subagents SHALL follow `gateway.notifications.background` in `concise` (default), `all`, `result`, `error`, `off` (unknown values fail validation), SHALL be injected as internal events whose acceptance is confirmed by a typed admission result, and a refused admission SHALL be retried later without consuming a delivery attempt.
**Milestone:** M2

#### Scenario: Errors only
- **GIVEN** `gateway.notifications.background = "error"`
- **WHEN** a background process exits 0
- **THEN** the system SHALL NOT notify the chat

### Requirement: Crash recovery and clean shutdown marker
A graceful stop whose drain completes within `gateway.shutdown.drain_timeout_secs` (default 30) SHALL write `<home>/run/clean_shutdown`; on start the daemon SHALL delete the marker and skip recovery when it exists, and otherwise SHALL mark every turn that was running at crash time `resume_pending` with `resume_reason = "restart_interrupted"`, notify each affected chat once with "The agent restarted while working on your last message. Reply /retry to run it again.", and resume the outbox; a failure to delete the marker SHALL abort startup with exit 1.
**Milestone:** M2

#### Scenario: Timed-out drain
- **WHEN** a stop's drain exceeds 30 seconds
- **THEN** the system SHALL NOT write `clean_shutdown` and the next start SHALL run recovery

### Requirement: Stuck-loop suspension
The gateway SHALL count, per session, consecutive daemon restarts during which that session's turn was active, persisting the counter in `state.db`, and SHALL suspend a session whose counter reaches `gateway.sessions.stuck_loop_threshold` (default 3) so its next message starts a new session; a turn that completes SHALL reset the counter, and suspension SHALL be the only automatic transition to `suspended`.
**Milestone:** M2

#### Scenario: Third restart suspends
- **GIVEN** a session active during two previous restarts
- **WHEN** it is active during a third
- **THEN** the system SHALL suspend it at startup and the next message SHALL start a new session with `reset_reason = "suspended"`

### Requirement: Agent cache and eviction
The gateway SHALL keep live agents in an LRU of at most `gateway.agent_cache.max_size` (default 128) with idle TTL `gateway.agent_cache.idle_ttl_secs` (default 3600) and SHALL shed least-recently-used agents when resident memory exceeds `gateway.agent_cache.memory_high_mb` (default `0` meaning auto at 50% of physical memory), never evicting an agent mid-turn or one whose transcript is not yet durable; eviction SHALL flush memory providers under the owning ProfileScope and SHALL NOT end the session, and a later message SHALL rebuild the agent from the stored transcript with an identical system prompt.
**Milestone:** M2

#### Scenario: Rebuilt agent preserves the cached prefix
- **GIVEN** a session's agent was evicted
- **WHEN** its next message arrives
- **THEN** the rebuilt agent SHALL produce a byte-identical system prompt and tool list to the evicted one

### Requirement: All adapters down policy
`gateway.on_all_adapters_down` SHALL accept `stay_alive` (default, because the daemon also serves local clients and schedulers) or `exit`; with `exit`, losing every messaging adapter to non-retryable errors SHALL stop the daemon with exit 78, and retryable losses SHALL keep reconnecting with backoff from 1 second up to 300 seconds.
**Milestone:** M2

#### Scenario: Revoked token keeps local clients alive
- **GIVEN** the only adapter's token is revoked and `on_all_adapters_down = "stay_alive"`
- **WHEN** the adapter reports a non-retryable fatal error
- **THEN** the daemon SHALL keep serving attached TUI and desktop clients and report the adapter as `fatal` in `gateway status`

### Requirement: Relay connector
When `gateway.relay.url` is set the gateway SHALL dial the relay connector over TLS authenticated by a secret named `gateway.relay.token_secret`, configure a `relay` adapter from the connector's capability descriptor (`contract_version` 1, unknown keys ignored, a missing or non-positive `max_message_length` treated as 4096 and logged), trust the connector's authorization (`authorization_is_upstream`), and SHALL disable the profile's direct adapters for platforms the relay fronts unless `gateway.relay.allow_direct_platforms` lists them; relay settings SHALL come only from configuration and the secrets store.
**Milestone:** M2

#### Scenario: Relay fronts Slack
- **GIVEN** the relay descriptor fronts `slack` and the profile also enables a direct Slack adapter
- **WHEN** the gateway starts
- **THEN** the system SHALL not connect the direct Slack adapter and SHALL log that the relay fronts it

### Requirement: Gateway health export is opt-in and content-free
The gateway SHALL export health metrics and lifecycle events only when `observability.gateway_health.enabled` is true (default `false`), limited to an allowlisted set of `prometheus.gateway.*`, `prometheus.adapter.*`, `prometheus.outbox.*` and `prometheus.cron.*` (the `prometheus.` metric prefix of `observability`) gauges and counters with bounded attributes (profile, platform, state, error code) and never message text, user ids, chat ids or secrets, and an unavailable export endpoint SHALL NOT affect message handling.
**Milestone:** M2

#### Scenario: Endpoint down
- **GIVEN** export enabled and the collector unreachable
- **WHEN** messages flow
- **THEN** the system SHALL keep handling them with unchanged latency budgets and log the export failure at most once per minute

### Requirement: Gateway lifecycle hooks are typed
The gateway SHALL emit only hooks from the closed registry owned by `plugin-system` — `on_gateway_startup`, `on_gateway_shutdown`, `on_session_start`, `on_session_end`, `on_session_reset`, `on_turn_start`, `on_turn_end`, `pre_command`, `pre_gateway_dispatch` (inbound message) and `post_gateway_delivery` (outbound message) — to plugin hooks registered for the event's profile; a plugin declaring a hook name outside that registry SHALL fail to load with an error naming it, and a hook error or timeout (`plugins.hook_timeout_ms`) SHALL be logged and SHALL NOT block the pipeline.
**Milestone:** M2

#### Scenario: Typo in hook name
- **WHEN** a plugin declares a hook for `on_sesion_start`
- **THEN** the system SHALL refuse to load the plugin and name `on_sesion_start` as unknown

#### Scenario: Secondary profile hook isolation
- **GIVEN** a hook installed only in profile `work`
- **WHEN** a default-profile session starts
- **THEN** the system SHALL NOT run `work`'s hook
